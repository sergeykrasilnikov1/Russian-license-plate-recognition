# Этап 1 — Структура проекта и окружение

- **Дата:** 2026-09-09
- **Статус:** завершён
- **Окружение:** Linux 6.8.0, Python 3.10.12, bash

## 1. Цель этапа

Создать репозиторий с фиксированной структурой каталогов из задания, закрепить
версии зависимостей, параметризовать список типов знаков (чтобы расширение на
новые типы/страны не требовало правок пайплайна) и подготовить точки входа для
Этапов 2–7.

## 2. Что сделано

### 2.1 Структура каталогов

Создано дерево `grz-recognition/` в точности по разделу 6 задания и Этапу 1 промпта:

```
grz-recognition/
  dataset/{images/{real,synthetic},labels,generator}/  meta.csv  README.md  LICENSE
  src/{detection,classification,ocr,pipeline,utils}/
  scripts/
  configs/
  docs/{reports/}
  weights/
  tests/
```

Дополнительно к заданию: `weights/` (веса поставляются вместе с решением, требование
офлайн-инференса), `tests/` (smoke-тесты), `docs/reports/` (отчёты по этапам).

### 2.2 Зависимости — две среды

Зависимости разделены на два файла, версии закреплены (`==`), чтобы окружение
воспроизводилось точно:

**`requirements-dev.txt`** — локальная машина **без GPU** (сбор данных, синтетика, тесты):

| Группа | Пакеты |
|--------|--------|
| Данные / изображения | `numpy==1.26.4`, `pandas==2.2.3`, `Pillow==11.0.0`, `opencv-python-headless==4.10.0.84`, `albumentations==1.4.21`, `scikit-learn` |
| Сбор данных | `requests`, `beautifulsoup4`, `lxml`, `huggingface_hub==0.26.5`, `roboflow==1.1.49`, `kaggle==1.6.17` |
| Приватность/дедуп (CPU) | `mediapipe==0.10.18`, `imagehash==4.3.1` |
| CLI / тесты | `click`, `rich`, `python-dotenv`, `pytest==8.3.4` |

**`requirements-train.txt`** — отдельный **GPU-сервер** (обучение, экспорт, инференс):

| Группа | Пакеты |
|--------|--------|
| Deep learning | `torch==2.5.1`, `torchvision==0.20.1`, `ultralytics==8.3.40` |
| OCR | `paddleocr==2.9.1`, `paddlepaddle-gpu==2.6.2` (сборка под CUDA сервера) |
| Экспорт / runtime | `onnx==1.17.0`, `onnxruntime-gpu==1.20.1` |

Единый `requirements.txt` удалён, чтобы среды не смешивались. Файл
`requirements-train.txt` также покрывает runtime для жюри: `onnxruntime` + `opencv`
достаточно для запуска `run_inference.py` с поставляемыми ONNX-весами.

### 2.3 Конфиги

- `configs/detector.yaml` — YOLOv11n, 4 класса (`type1`, `type1a`, `type1b`, `other`),
  гиперпараметры обучения, `seed: 42`, параметры экспорта в ONNX и порогов инференса.
- `configs/ocr.yaml` — алфавит ГРЗ (`0-9` + `ABEKMHOPCTYX` + `#`), regex маски номера,
  размеры warp по типам, три baseline-кандидата (PP-OCRv4_mobile / PP-OCRv5_mobile /
  PARSeq) и режим агрегации confidence.
- `configs/pipeline.yaml` — пути к весам, провайдеры ONNX Runtime (CUDA → CPU),
  эвристика `is_vehicle`, бюджет latency 100 мс, расширения входных файлов.

### 2.4 Код

- `src/utils/plate_mask.py` — валидация маски `[БУКВА][ЦИФРА×3][БУКВА×2][РЕГИОН]`:
  нормализация (верхний регистр, удаление пробелов/дефисов, перевод кириллических
  двойников в латиницу), проверка алфавита, проверка кода региона (2 цифры или
  3 цифры, начинающиеся с 1/2/7), поддержка `#` для нечитаемых позиций.
- `src/utils/geometry.py` — реестр `PLATE_TYPES` с геометрией по ГОСТ Р 50577-2018
  (type1 520×112, type1a 290×170 две строки, type1b 520×112 жёлтый) плюс мэппинг
  class_id ↔ имя. Это единственное место, куда добавляется новый тип знака.
- Пакеты `src/{detection,classification,ocr,pipeline}` с docstring-описанием роли.
  В `classification/__init__.py` явно зафиксировано, что тип знака определяется
  классом bbox в детекторе (экономия latency), а пакет оставлен под эвристику
  vehicle-контекста.

### 2.5 Точки входа

| Скрипт | Состояние |
|--------|-----------|
| `scripts/validate_dataset.py` | **работает** — проверяет схему `meta.csv`, наличие LICENSE/README/каталогов, пишет отчёт |
| `scripts/scrape_real_data.py` | CLI-каркас (`--out`, `--seed`, `--sources`), Этап 2 |
| `scripts/build_synthetic.py` | CLI-каркас (`--count`, `--seed`, `--type-weights`), Этап 3 |
| `scripts/train_detector.py` | CLI-каркас, Этап 4 |
| `scripts/train_ocr.py` | CLI-каркас, Этап 5 |
| `scripts/benchmark_latency.py` | CLI-каркас, Этап 5/6 |
| `scripts/run_inference.py` | CLI-каркас с поддержкой `--input/--output` и переменных `GRZ_INPUT_DIR`/`GRZ_OUTPUT_CSV`, Этап 6 |

Незавершённые скрипты бросают `NotImplementedError` с указанием этапа — они не
возвращают тихо пустой результат, который можно принять за рабочий.

### 2.6 Документация и лицензии

- `README.md` — требования, быстрый старт, команда запуска инференса, таблица скриптов.
- `dataset/README.md` — каркас датащита; **честно зафиксировано**, что первичная
  разметка получается автоматически (детектор + OCR) с программной валидацией по
  маске и не является ручной проверкой человеком.

## 4. Соответствие ограничениям задания

| Ограничение | Как учтено на Этапе 1 |
|-------------|------------------------|
| Офлайн-инференс | `configs/pipeline.yaml` ссылается только на локальные веса; `weights/` в поставке |
| ≤ 100 мс/изображение | `latency_budget_ms: 100` в конфиге, отдельный скрипт замера |
| Веса вместе с решением | каталог `weights/`, никаких скачиваний в runtime |
| Формат номера и алфавит | реализовано в `plate_mask.py`, покрыто тестами |
| Лицензии данных | CC BY 4.0 в `dataset/LICENSE`, поля `source`/`license` в `meta.csv` |
| Честность разметки | явная дисклеймер-секция в `dataset/README.md` |
| Расширяемость на новые типы | `PLATE_TYPES` + `names` в `detector.yaml`, без хардкода в пайплайне |

## 5. Разделение сред (зафиксировано, не проблема)

Локальная машина — **без GPU**. `torch`, `torchvision`, `ultralytics`, `paddlepaddle`
здесь **сознательно не устанавливаются**: они перечислены в `requirements-train.txt`
и ставятся только на GPU-сервере. Отсутствие `import torch` локально — ожидаемое
состояние проекта, а не дефект окружения и не блокер.

Как это влияет на этапы:

| Этап | Где выполняется | Комментарий |
|------|-----------------|-------------|
| 1 | локально | выполнен полностью |
| 2 (сбор данных) | локально | скрапинг + mediapipe/imagehash — CPU-only |
| 3 (синтетика) | локально | Pillow/OpenCV/albumentations — CPU-only |
| 4 (детектор) | GPU-сервер | код пишется локально, запуск на сервере |
| 5 (OCR) | GPU-сервер | то же |
| 6 (инференс, latency) | GPU-сервер / референсное железо | то же |

Для кода Этапов 4–6 действует правило: локально покрываются тестами только части,
не требующие torch/paddleocr (валидация конфигов, парсинг CLI, чистые функции,
сборка CSV через `unittest.mock`), и в отчёте каждого такого этапа явно
указывается, что код не выполнялся физически.

## 6. Прочие открытые вопросы

1. **Локальные зависимости ставились точечно** — на момент Этапа 1 тесты используют
   только стандартную библиотеку и `pytest`; полная установка `requirements-dev.txt`
   относится к Этапу 2.
2. **Синтетика из более раннего прогона утеряна** — набор генерируется заново на
   Этапе 3. Причина потери — запись артефактов и логов вне репозитория; отсюда
   правило: все генерируемые данные пишутся только внутрь `grz-recognition/`,
   плюс git-коммит после каждого этапа.
